RFC / 0011

Portal for RFCs and framework definitions

Draft · authored by donald · revision 4 · 2 hours ago

#Summary

An internal web portal that renders Markdown RFCs from a single Git repo (rfcs) as a nicer read experience than raw GitHub. Full-text search, cross-document linking, and a public read API. Authorship stays in Git; the portal is read-only. Deployed to Kubernetes via a Helm chart in the same repo.

Note

This RFC describes phase 1 — the RFC reading experience. A future RFC will cover rendering our custom Wiz security frameworks as a second content source, reusing the same ingester and API layer.

#Motivation

RFCs live as Markdown in Git. Reading them means cloning the repo or browsing GitHub, neither of which gives cross-document search, hover previews on RFC references, or a clean shareable URL for non-developers.

The Oxide rfd-site project (see RFC-0008RFC / 0008Wiz CSPM deployment and scopeACCEPTED·donald, priya·Feb 2025) validates the shape of the solution; we want the same reading experience against our Markdown + docz conventions with our stack and auth.

#Goals

  • Unified read experience for RFCs in the rfcs repo.
  • Full-text search with Meilisearch.
  • Cross-document linking with hover previews (title, status, author, last-updated).
  • Live Git sync within a few minutes of a merge to main.
  • Public read API — curl-friendly JSON endpoints.
  • Fits on the existing Kubernetes cluster; single Helm chart deploys the whole thing.

#Architecture

Three components, one Helm chart, one repo. The ingester and API are the same Go binary in different subcommand modes; the frontend is a separate Bun + React service.

┌────────────────┐ ┌────────────────┐ │ rfcs repo │ push │ ingester │ │ (github) ├────────▶│ (go, 10m) │ └────────────────┘ webhook └───────┬────────┘ │ ┌──────────────────────┼──────────────────────┐ ▼ ▼ ▼ ┌────────────┐ ┌────────────┐ ┌────────────┐ │ postgres │ │ meili │ │ object fs │ │ metadata │ │ search │ │ (future) │ └──────┬─────┘ └──────┬─────┘ └────────────┘ │ │ └───────────┬───────────┘ ▼ ┌──────────────────┐ │ api (go) │ │ /api/v1/rfcs │ └─────────┬────────┘ ▲ ┌─────────┴────────┐ │ frontend │ │ (bun + react) │ └──────────────────┘

Components

API (Go). HTTP service, stateless, reads Postgres + Meilisearch. Reuses docz Go code for Markdown + frontmatter parsing to guarantee the portal's understanding of an RFC matches the CLI's.

Ingester. Same Go binary, different subcommand. Periodic reconcile loop plus optional GitHub webhook endpoint.

Frontend (Bun + React). Server-rendered. Replicates the RFC-0008RFC / 0008Wiz CSPM deployment and scopeACCEPTED·donald, priya·Feb 2025 reading experience: cmd+K search, hover previews on cross-RFC references, jump-to navigation.

Data model

Two tables. Documents are keyed by their zero-padded RFC number; cross-references are computed at ingest time and stored as directed edges.

Table 1. documents schema
Column Type Notes
id text Zero-padded RFC number, e.g. "0011". Primary key.
source_path text Relative path in the repo, e.g. rfc/0011-portal.md.
source_ref text Commit SHA this record was derived from. Used to skip unchanged files on reconcile.
title text From frontmatter.
status text One of: Draft, Proposed, Accepted, Rejected, Superseded. Validated at ingest.
authors text[] Array of author handles from frontmatter.
labels text[] Array, also from frontmatter.
frontmatter jsonb Full parsed frontmatter, preserved for extension.
body_markdown text Raw source.
body_html text Pre-rendered HTML, cached for API response speed.
created_at timestamptz Earliest commit that introduced the file.
updated_at timestamptz Commit that produced source_ref.

Frontmatter is parsed by the existing docz library:

go internal/ingest/parse.go 
package ingest

import (
    "context"
    "fmt"

    "github.com/donaldj/docz/frontmatter"
    "github.com/yuin/goldmark"
)

// ParseRFC reads a Markdown file, extracts frontmatter using the docz
// parser, renders the body to HTML, and returns a normalized Document.
func ParseRFC(ctx context.Context, path string, raw []byte) (*Document, error) {
    fm, body, err := frontmatter.Split(raw)
    if err != nil {
        return nil, fmt.Errorf("parse %s: %w", path, err)
    }

    var buf bytes.Buffer
    if err := goldmark.Convert(body, &buf); err != nil {
        return nil, fmt.Errorf("render %s: %w", path, err)
    }

    return &Document{
        ID:           fm.RFCNumber(),
        Title:        fm.Title,
        Status:       fm.Status,
        Authors:      fm.Authors,
        Labels:       fm.Labels,
        BodyMarkdown: string(body),
        BodyHTML:     buf.String(),
    }, nil
}

#Ingest flow

The ingester runs on a schedule and reconciles the desired state (the contents of main) with the stored state (what's in Postgres). Each iteration is idempotent; missed runs are recovered on the next tick.

Fig 1. Reconcile loop. Webhook pushes trigger the same flow out-of-schedule.
Tip

The reconcile is intentionally idempotent. Operators can force a reindex by truncating documents.source_ref and waiting for the next tick — no special tooling required.

Warning

GitHub webhooks are best-effort. Do not rely on them for correctness — the reconcile loop is the source of truth. If webhooks are delayed or lost, the worst case is 10 minutes of stale content.

#Rollout

Four phases, each independently shippable.

Table 3. Rollout phases
Phase Scope Estimate
1 Read-only portal, periodic reconcile, Meilisearch, no auth 2–4 weekends
2 Webhook ingest, hover previews, cmd+K, print styles 1–2 weekends
3 Okta OIDC on frontend, admin endpoints 1 weekend
4 Wiz framework rendering (separate RFC) TBD
Caution

Okta integration is deferred to phase 3, but the portal will be on a public ingress before then. If content sensitivity demands it, put a cluster-internal ingress in front of phase 1 and defer public exposure until phase 3 ships.

#Open Questions

  1. Webhooks in v1 or v2? Leaning v2. Polling is simpler and works without inbound exposure.
  2. Frontend framework — Next.js, Remix, or something lighter? Defer to the implementer.
  3. Does this absorb ADRs and other docz types? Same format, trivial to include. UX question of one unified directory vs per-type sections. Recommend RFC-only in v1.
The periodic reconcile is the source of correctness. Webhooks are an optimization; a missed webhook costs at most 10 minutes of staleness.

RFC / 0125

Okta group → Wiz SAML access provisioning

Accepted · donald, priya · 3 days ago

Summary

An automated workflow using Zluri → JSM → Go service → Okta to provision Wiz SAML application access based on Okta group membership. Eliminates manual ticket-driven access grants for Wiz's console.

Motivation

Today, granting a developer access to Wiz requires a manual ticket through JSM, which routes to the security team, who manually add the user to the Wiz SAML application in Okta. This creates a 1–3 day delay and a consistent backlog in the security queue.

Since we already represent team membership and role in Okta groups, and since Wiz access follows directly from team role, this mapping can be fully automated.

Proposed Solution

Introduce a Go service (wiz-access-sync) that reads Okta group membership on a 5-minute cadence and reconciles it to Wiz SAML application assignments via the Okta Admin API…

Model Context Protocol

Pull RFCs directly into your editor.

The portal ships a small MCP server that exposes the read API as callable tools. Connect Claude Code, Cursor, or any MCP-aware client and search, fetch, and reference RFCs without leaving your editor. The same server also serves as the reference implementation for our internal docs.

rfcs-mcp
this server

Exposes the portal's RFC read API as MCP tools — list_rfcs, get_rfc, search_rfcs, get_links. No write operations; authoring still happens in Git.

3Available tools

Once connected, the following tools are available to your LLM. All are read-only and safe to invoke without confirmation.

  • list_rfcs — list all RFCs with optional status and label filters. Returns id, title, status, authors, updated_at.
  • get_rfc — fetch a single RFC by id, including rendered markdown body and resolved cross-references.
  • search_rfcs — full-text search across titles, bodies, authors, and labels. Returns ranked results with highlighted snippets.
  • get_links — get the full reference graph for an RFC: what it references, what references it, and transitive depth.
  • get_activity — recent changes across all RFCs, useful for "what's happening this week" prompts.

4Verify it works

Restart your client and ask it to summarize a recent RFC. The client should invoke get_rfc and return a coherent summary. A good sanity check prompt:

# in your LLM chat:
"Summarize RFC 0011 in three bullet points and list any RFCs it references."

CIS 1.8

Ensure IAM password policy requires minimum length of 14 or greater

Medium · compliance: passing · last checked: 42 min ago · applies to: 187 accounts
Description

Password policies are used to enforce password complexity requirements. IAM password policies can be used to ensure passwords are of a given length. It is recommended that the password policy require a minimum password length of 14 characters.

Setting a password complexity policy increases account resiliency against brute-force login attempts.

Rationale

A minimum password length of 14 characters significantly increases resistance to brute-force attacks. Our baseline chose 14 over the CIS-recommended minimum of 8 based on RFC-0006, which cites current NIST guidance and internal threat modeling.
